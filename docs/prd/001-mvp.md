# Product Requirements Document (PRD)

**Project:** Online Judge (LeetCode-like MVP)
**Author:** Yash Kumar Gupta
**Stage:** MVP

---

# 1. Objective

Build a minimal Online Judge platform where users can:

* browse coding problems
* submit solutions
* receive automated verdicts

The primary goal is:

* demonstrate strong **MERN stack skills**
* build a **production-style async system**
* keep infra **low-cost using serverless (GCP)**

---

# 2. Target Users

### Primary

* Students practicing DSA
* You (as developer, for showcasing skills)

### Secondary (later)

* Competitive programmers
* Interview prep users

---

# 3. Core Features (MVP Scope)

## 3.1 User System

* Register / Login
* Basic authentication (JWT)

---

## 3.2 Problem System

# 5. Functional Requirements

---

## 5.1 Problem APIs

* `GET /problems` → list problems
* `GET /problems/:slug` → problem details

---

## 5.2 Submission APIs

* `POST /submissions`

  * input: `{ code, language, problemId }`
  * output: `{ submissionId }`

* `GET /submissions/:id`

  * returns status + result

---

## 5.3 Execution Flow

1. User submits code
2. Submission stored (`pending`)
3. Event sent to Pub/Sub
4. Cloud Run worker executes code
5. Submission updated with result

---

## 5.4 State Transitions

```text
pending → running → accepted | wrong_answer | tle | re
```

---

# 6. System Architecture

### High-Level Flow

```text
Frontend (React)
        ↓
Backend API (Node.js / Express - Cloud Run)
        ↓
MongoDB (Database)
        ↓
Pub/Sub (Event Queue)
        ↓
Cloud Run Worker (Execution Engine)
        ↓
Database अपडेट
```

---

# 7. Data Model (MVP)

Collections:

* `users`

* `submissions`

Key relationships:

```text
User → Submissions
Problem → Testcases
```

---

# 8. Non-Functional Requirements

---

## 8.1 Performance

* API response < 300ms (excluding execution)
* Execution async (no blocking)

---

## 8.2 Scalability

* Use serverless (Cloud Run auto-scaling)
* Pub/Sub for decoupling

---

## 8.3 Cost Constraints

* Must stay within free tier initially
* No dedicated VMs

---

## 8.4 Reliability

* Submissions should not be lost
* System should tolerate retries

---

## 8.5 Security (basic for MVP)

* Code execution must be sandboxed
* Prevent arbitrary system access

---

# 9. Success Metrics

For MVP success:

* User can solve at least 1 problem end-to-end
* Submission success rate > 95%
* No stuck submissions (or minimal)
* System runs within free tier

# 11. Risks & Assumptions

---

## Risks

* Code execution sandbox complexity
* Cloud Run limitations (timeouts, resources)
* Handling infinite loops / heavy programs

---

## Assumptions

* Low initial traffic
* Limited concurrency acceptable
* Users tolerate polling for results
